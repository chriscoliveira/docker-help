Conceitos em um minuto

Se você guardar só uma ideia: container é descartável, dados importantes ficam em volume. O resto deriva disso.

ImagemPacote pronto e somente leitura (sistema + app + dependências). Ex.: nginx:1.27.
ContainerUma imagem em execução. Você cria, para, apaga e recria quantos quiser.
VolumePasta que vive fora do container. Sobrevive quando o container é apagado.
RedeComo containers conversam entre si e com o mundo. Em rede própria, um acha o outro pelo nome.
RegistryRepositório de imagens. O padrão é o Docker Hub (docker pull baixa de lá).
ComposeUm arquivo YAML que descreve vários containers, volumes e redes e sobe tudo com um comando.

Analogia rápida: imagem é a receita do bolo, container é o bolo pronto, volume é a geladeira onde você guarda o que não pode se perder.

Primeiros passos (Ubuntu)

Instalação oficial: docs.docker.com/engine/install/ubuntu. Depois, confira se está tudo certo:

docker --version
docker compose version

Mostra as versões. O Compose moderno é docker compose (com espaço), não docker-compose.

docker run hello-world

Teste completo: baixa uma imagem minúscula, cria um container e imprime uma mensagem de sucesso.

sudo usermod -aG docker $USER
newgrp docker

Permite usar docker sem sudo. O newgrp vale para o terminal atual; nas demais sessões, saia e entre de novo.

sudo systemctl enable --now docker
sudo systemctl status docker

Liga o serviço agora e em todo boot, e mostra o estado dele.

docker info

Resumo do daemon: quantos containers/imagens, driver de armazenamento, pasta de dados (Docker Root Dir).

docker --help
docker container --help
docker run --help

A ajuda embutida é boa e mostra todas as flags. Use sempre que esquecer algo.

Imagens

docker pull nginx:1.27

Baixa uma imagem. Depois dos dois-pontos vem a tag (versão). Sem tag, vira latest.

docker images
docker image ls

Lista as imagens locais, com tamanho e data.

docker search redis

Procura no Docker Hub. Prefira imagens marcadas como Official.

docker build -t meuapp:1.0 .

Constrói uma imagem a partir do Dockerfile da pasta atual (o . no final é o contexto).

docker build --no-cache -t meuapp:1.0 .

Ignora o cache e refaz todas as etapas. Use quando algo "não atualiza".

docker tag meuapp:1.0 meuusuario/meuapp:1.0

Dá outro nome à mesma imagem (necessário antes de enviar ao Docker Hub).

docker login
docker push meuusuario/meuapp:1.0

Entra no registry e envia a imagem.

docker rmi nginx:1.27

Remove uma imagem (falha se algum container ainda a usa).

docker history meuapp:1.0
docker inspect meuapp:1.0

history mostra as camadas e o tamanho de cada uma. inspect despeja todos os metadados em JSON.

docker save -o meuapp.tar meuapp:1.0
docker load -i meuapp.tar

Exporta/importa uma imagem como arquivo. Útil para levar para uma máquina sem internet.

Containers

Criar e rodar

docker run -d --name web -p 8080:80 nginx:1.27

O comando mais importante. Sobe o Nginx em segundo plano, com nome web, e acessível em http://localhost:8080.

FlagO que faz
-dRoda em segundo plano (detached). Sem ela, o terminal fica preso ao container.
--name xNome fácil em vez do aleatório. Precisa ser único.
-p 8080:80Porta host:container. A da esquerda é a do seu PC, a da direita é a do app dentro.
-v dados:/pastaMonta volume ou pasta. Veja a seção Volumes.
-e VAR=valorDefine variável de ambiente. Também existe --env-file .env.
--rmApaga o container quando ele termina. Ótimo para testes.
-itModo interativo com terminal (para entrar em um shell).
--restart unless-stoppedVolta sozinho após falha ou reboot, a menos que você o tenha parado.
--network redeConecta a uma rede específica.
-u $(id -u):$(id -g)Roda com o seu usuário (evita arquivos criados como root).
docker run --rm -it ubuntu:24.04 bash

Abre um Ubuntu descartável para testar comandos. Ao sair (exit), tudo é apagado.

Ver o que está acontecendo

docker ps
docker ps -a

ps mostra os que estão rodando; -a inclui os parados e os que falharam.

docker logs -f --tail 100 web
docker logs --since 10m web

Saída do container. -f acompanha em tempo real, --tail limita as últimas linhas, --since filtra por tempo.

docker stats
docker top web

stats mostra CPU, memória e rede ao vivo. top lista os processos dentro do container.

docker inspect web
docker inspect -f '{{.State.ExitCode}}' web
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web

Detalhes completos em JSON. Com -f você extrai só um campo (código de saída, IP, etc.).

docker port web

Mostra o mapeamento de portas do container.

Interagir

docker exec -it web bash
docker exec -it web sh

Abre um terminal dentro de um container que já está rodando. Imagens enxutas (alpine) só têm sh.

docker exec web nginx -t

Executa um comando pontual sem abrir shell.

docker cp web:/etc/nginx/nginx.conf ./nginx.conf
docker cp ./index.html web:/usr/share/nginx/html/

Copia arquivos entre o container e o seu PC, nos dois sentidos.

Ciclo de vida

docker stop web      # pede para parar com educação (SIGTERM)
docker start web     # liga de novo
docker restart web
docker kill web      # mata na hora (SIGKILL)

Parar não apaga nada: o container continua existindo, só desligado.

docker rm web
docker rm -f web     # para e remove de uma vez

Remove o container. Dados que estavam só dentro dele são perdidos; volumes permanecem.

docker rename web site

Renomeia um container existente.

docker update --restart unless-stopped web

Muda a política de reinício de um container que já existe.

Volumes e persistência

Tudo que o container grava dentro dele some quando ele é removido. Para guardar dados, use um destes dois modos:

TipoComo escreverQuando usar
Volume nomeado-v dados:/var/lib/appBancos de dados e dados do app. O Docker gerencia o local (/var/lib/docker/volumes).
Bind mount-v $(pwd)/site:/usr/share/nginx/htmlVocê quer editar arquivos do seu PC e ver o efeito no container (código, configs).
docker run -d --name db -v dados:/var/lib/postgresql/data -e POSTGRES_PASSWORD=troque postgres:16

Volume nomeado: se você apagar e recriar o container db com o mesmo -v, os dados continuam lá.

docker run -d -p 8080:80 -v $(pwd)/site:/usr/share/nginx/html:ro nginx:1.27

Bind mount. O :ro deixa somente leitura dentro do container, mais seguro para configs e sites estáticos.

docker volume ls
docker volume inspect dados
docker volume create dados
docker volume rm dados

Gerenciar volumes. inspect mostra onde ele está no disco.

docker run --rm -v dados:/data -v $(pwd):/backup alpine tar czf /backup/dados.tar.gz -C /data .

Backup de um volume: um container temporário compacta o conteúdo para a sua pasta atual.

docker run --rm -v dados:/data -v $(pwd):/backup alpine tar xzf /backup/dados.tar.gz -C /data

Restaurar o backup acima em um volume.

Dica com arquivos únicos (SQLite, por exemplo): monte a pasta que contém o arquivo, não o arquivo em si. Alguns editores recriam o arquivo ao salvar e o bind mount de arquivo único passa a apontar para o antigo.

Redes

Na rede padrão (bridge) os containers só se acham por IP. Em uma rede criada por você, eles se acham pelo nome do container.

docker network create minharede
docker run -d --name db --network minharede postgres:16
docker run -d --name app --network minharede -p 8000:8000 meuapp:1.0

Dentro do app, o banco é acessado em db:5432. Não precisa de IP nem de -p para a comunicação interna.

docker network ls
docker network inspect minharede
docker network connect minharede web
docker network disconnect minharede web

Listar, inspecionar (mostra quem está conectado e os IPs) e mover containers entre redes.

docker run --rm -it --network host alpine sh

--network host usa a rede do próprio host, sem isolamento e sem -p. Só em Linux; útil para diagnóstico.

docker run --add-host=host.docker.internal:host-gateway ...

No Linux, é assim que o container enxerga serviços rodando na máquina host (usando o nome host.docker.internal).

Lembrete: -p é para acessar de fora (seu navegador, outra máquina). Entre containers da mesma rede, use o nome e a porta interna.

Dockerfile

Receita para montar a sua própria imagem. Exemplo típico para um script Python:

FROM python:3.12-slim
WORKDIR /app

# dependências primeiro (aproveita o cache)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# depois o código
COPY . .

ENV TZ=America/Sao_Paulo
CMD ["python", "main.py"]

Salve como Dockerfile e rode docker build -t meuapp:1.0 .. Depois: docker run -d --name meuapp meuapp:1.0.

InstruçãoFunção
FROMImagem base. Prefira tags -slim ou -alpine e fixe a versão.
WORKDIRPasta de trabalho dentro da imagem (é criada se não existir).
COPYCopia arquivos do seu PC para a imagem.
RUNExecuta um comando durante o build (instalar pacotes, por exemplo).
ENVVariável de ambiente que fica na imagem.
EXPOSEApenas documenta a porta do app. Não publica nada; quem publica é o -p.
CMDComando padrão ao iniciar o container (pode ser sobrescrito no docker run).
ENTRYPOINTComando fixo; o que vier no docker run vira argumento dele.
__pycache__/
*.pyc
.git
.env
venv/
node_modules/

Arquivo .dockerignore: o que não deve ir para o build. Deixa o build mais rápido e evita vazar segredos na imagem.

Ordem importa para o cache. Cada linha vira uma camada. Coloque primeiro o que muda pouco (dependências) e por último o que muda sempre (seu código). Assim o rebuild leva segundos.

Docker Compose

Em vez de decorar vários docker run longos, descreva tudo em um compose.yaml e use um comando. Exemplo com Nginx servindo uma pasta e um app com volume:

services:
  web:
    image: nginx:1.27
    ports:
      - "8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro
    depends_on:
      - app
    restart: unless-stopped

  app:
    build: .
    env_file: .env
    environment:
      - TZ=America/Sao_Paulo
    volumes:
      - dados:/app/data
    restart: unless-stopped

volumes:
  dados:

Cada item em services vira um container. Todos entram numa rede comum automaticamente, então web acessa app pelo nome (http://app:8000). A linha version: não é mais necessária.

docker compose up -d

Cria e inicia tudo em segundo plano.

docker compose up -d --build

Reconstrói as imagens (as com build:) antes de subir. Use depois de mexer no código ou no Dockerfile.

docker compose ps
docker compose logs -f app

Estado dos serviços e logs de um deles (sem o nome, mostra todos).

docker compose exec app sh
docker compose run --rm app python teste.py

exec entra em um serviço que está rodando. run --rm cria um container novo só para um comando.

docker compose restart app
docker compose stop
docker compose start

Reinicia um serviço, ou para/liga tudo sem remover.

docker compose pull
docker compose up -d

Baixa versões novas das imagens e recria só o que mudou.

docker compose config

Valida o YAML e mostra o resultado final com variáveis resolvidas. Ótimo para achar erro de indentação.

docker compose down

Para e remove containers e redes. Os volumes ficam.

Cuidado: docker compose down -v também apaga os volumes, ou seja, os dados. Só use quando quiser zerar tudo.

Limpeza e espaço em disco

Com o tempo, imagens antigas, containers parados e cache de build ocupam muito disco.

docker system df

Mostra quanto espaço cada categoria usa e quanto é "recuperável".

docker container prune      # remove containers parados
docker image prune          # remove imagens sem tag (dangling)
docker image prune -a       # remove todas as imagens sem uso
docker builder prune        # limpa o cache de build

Limpezas seletivas. Cada uma pede confirmação.

docker system prune -a

Limpa containers parados, redes sem uso, imagens sem uso e cache. Não mexe em volumes.

Cuidado com volumes: docker volume prune e docker system prune --volumes apagam volumes que nenhum container esteja usando naquele momento. Se o container do banco estiver parado, o volume dele entra na lista. Rode docker volume ls antes.

Problemas comuns e como resolver

Clique no sintoma para abrir a causa e a solução. A busca lá em cima também procura aqui.

Como investigar (roteiro geral)

docker ps -a                                # o container existe? está Up ou Exited?
docker logs --tail 100 NOME                 # o que ele disse antes de cair?
docker inspect -f '{{.State.ExitCode}}' NOME  # com qual código saiu?
docker exec -it NOME sh                     # entrar e olhar por dentro
docker events                               # eventos do daemon em tempo real

Nessa ordem, resolve a maioria dos casos. Quase sempre a resposta está em docker logs.

permission denied while trying to connect to the Docker daemon socket

Causa: seu usuário não está no grupo docker.

sudo usermod -aG docker $USER
newgrp docker      # ou saia e entre de novo na sessão
docker ps          # testar
Cannot connect to the Docker daemon. Is the docker daemon running?

Causa: o serviço do Docker está parado.

sudo systemctl start docker
sudo systemctl enable docker
sudo journalctl -u docker -n 50 --no-pager   # se não subir, veja o motivo aqui
port is already allocated / address already in use

Causa: a porta do host já está em uso por outro container ou por outro programa.

docker ps --format "table {{.Names}}\t{{.Ports}}"   # algum container já usa?
sudo ss -tulpn | grep :8080                          # ou algum processo do sistema?

Solução: pare quem está usando, ou mude o lado esquerdo do -p (ex.: -p 8081:80). A porta de dentro do container não muda.

The container name "/x" is already in use

Causa: já existe um container (talvez parado) com esse nome.

docker rm -f x
# depois rode o docker run de novo

Para testes, use --rm e isso não acontece mais.

O container sobe e cai na hora (status Exited)

Causa: o processo principal terminou ou deu erro. Um container só vive enquanto o processo principal roda em primeiro plano.

docker logs NOME
docker inspect -f '{{.State.ExitCode}}' NOME
  • 0: o programa terminou normalmente (era um script que acabou, ou o serviço foi para segundo plano).
  • 1: erro na própria aplicação, veja os logs.
  • 125 / 126 / 127: erro do Docker, comando sem permissão de execução ou comando não encontrado (confira o CMD).
  • 137: morto à força, geralmente falta de memória (OOM) ou docker kill.
  • 139: falha de segmentação no programa.

Para investigar por dentro, troque o comando por um shell:

docker run --rm -it --entrypoint sh IMAGEM
O container está rodando mas não abre no navegador

Checklist:

  • O -p está certo? docker port NOME mostra o mapeamento.
  • O app dentro do container escuta em 0.0.0.0? Se escutar só em 127.0.0.1, nada de fora chega. Em Flask, por exemplo, use host="0.0.0.0".
  • A porta do lado direito do -p é a mesma que o app usa?
  • Teste de dentro: docker exec NOME curl -s localhost:PORTA. Funciona lá dentro e não fora? Então é bind/porta/firewall.
Firewall (ufw) liberado só para algumas portas, mas o container aparece para todo mundo

Causa: o Docker escreve direto no iptables e ignora as regras do ufw para portas publicadas com -p.

Solução: publique só no localhost quando não quiser expor na rede:

docker run -d -p 127.0.0.1:8080:80 nginx:1.27
# no compose:  - "127.0.0.1:8080:80"

Aí um proxy (como o Nginx do host) decide o que fica público.

no space left on device

Causa: imagens, cache de build, volumes ou logs encheram o disco.

docker system df
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail   # logs gigantes?
docker system prune -a      # limpa sem uso (não mexe em volumes)

Se os logs forem o problema, veja o item abaixo para limitá-los.

Logs dos containers crescendo sem parar

Causa: por padrão o Docker não limita o tamanho do log de cada container.

Solução global (vale para containers novos; os existentes precisam ser recriados):

sudo nano /etc/docker/daemon.json

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

sudo systemctl restart docker

Só em um serviço do Compose:

    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

Se já houver um daemon.json, una as chaves no mesmo arquivo (é um único JSON válido). Reiniciar o Docker derruba containers que não tenham restart configurado.

Alterei o código, mas o container continua com a versão antiga

Causa: a imagem não foi reconstruída, ou o container antigo continua rodando.

docker compose up -d --build           # Compose
docker build --no-cache -t meuapp:1.0 .  # sem Compose, ignorando cache
docker rm -f meuapp
docker run -d --name meuapp meuapp:1.0   # recria o container com a imagem nova

Para imagens do Docker Hub com tag latest, use antes docker pull ou docker compose pull. Durante o desenvolvimento, um bind mount da pasta do código evita rebuild a cada mudança.

Meus dados sumiram depois de recriar o container

Causa: os dados estavam dentro do container, sem volume. Ou você usou docker compose down -v / docker volume prune.

Prevenção: monte um volume na pasta onde o app grava (banco, uploads, arquivos .db). Confira o caminho na documentação da imagem, por exemplo /var/lib/postgresql/data no Postgres. Faça backup periódico com o comando da seção Volumes.

Arquivos criados pelo container ficam como root no meu PC (permission denied ao editar/apagar)

Causa: por padrão o processo roda como root dentro do container, e os arquivos do bind mount herdam esse dono.

docker run --user $(id -u):$(id -g) -v $(pwd):/app ...   # roda com o seu usuário
sudo chown -R $USER:$USER pasta/                         # corrige o que já foi criado

No Compose: user: "1000:1000" no serviço (ajuste para o seu id -u).

Container sem internet ou sem resolver nomes (DNS)

Teste:

docker run --rm alpine ping -c 2 8.8.8.8      # testa a saída pela rede
docker run --rm alpine nslookup google.com    # testa DNS

Se o ping funciona e o DNS não, force um DNS no /etc/docker/daemon.json (por exemplo o do seu servidor interno) e reinicie o Docker:

{ "dns": ["8.8.8.8", "1.1.1.1"] }

Se nem o ping funciona, veja se o encaminhamento de pacotes e o firewall do host estão liberados, e se há VPN interferindo.

Conflito com a rede da empresa (Docker usa 172.17.0.0/16 e some acesso a algo)

Causa: o Docker escolhe faixas privadas (172.17.x.x e outras) para as próprias redes. Se a sua rede ou VPN usa a mesma faixa, o tráfego vai para o lugar errado.

Solução: defina outras faixas no /etc/docker/daemon.json:

{
  "bip": "10.199.0.1/24",
  "default-address-pools": [
    { "base": "10.200.0.0/16", "size": 24 }
  ]
}

sudo systemctl restart docker

Escolha uma faixa que não exista na sua rede. Redes já criadas mantêm a faixa antiga até serem recriadas (docker compose down e up).

Horário errado dentro do container (fuso UTC)

Causa: imagens usam UTC por padrão.

docker run -e TZ=America/Sao_Paulo ...
# Compose:
    environment:
      - TZ=America/Sao_Paulo

Em imagens muito enxutas pode ser preciso instalar o pacote tzdata.

Chrome/Selenium travando ou caindo dentro do container

Causa: o Chrome usa bastante /dev/shm, e o Docker dá só 64 MB por padrão.

docker run --shm-size=2g ...
# Compose:
    shm_size: "2gb"

Nas opções do Chrome também ajudam --disable-dev-shm-usage e, em container, --no-sandbox. Rode em modo --headless=new quando não precisar da tela.

exec: "bash": executable file not found

Causa: imagens enxutas, como as baseadas em alpine, não têm bash.

docker exec -it NOME sh
toomanyrequests: You have reached your pull rate limit

Causa: o Docker Hub limita downloads anônimos por IP. Em rede corporativa, muita gente compartilha o mesmo IP.

docker login

Logado, o limite é bem maior. Em ambiente com muitas máquinas, considere um espelho local (registry cache).

Erro de YAML no Compose (yaml: line X ... / mapping values are not allowed)

Causa: quase sempre indentação. YAML usa espaços, nunca tab, e a hierarquia depende da quantidade.

docker compose config

Esse comando aponta a linha do erro. Cuidado também com : em valores (coloque entre aspas) e com portas sem aspas, como "8080:80".

docker-compose: command not found (ou comportamento diferente do esperado)

Causa: o docker-compose (v1, com hífen) foi descontinuado. O atual é um plugin do Docker.

docker compose version

Se não existir, instale o pacote docker-compose-plugin seguindo a documentação oficial. Todos os comandos são iguais, só troque o hífen por espaço.

Depende de outro serviço, mas o app sobe antes do banco estar pronto

Causa: depends_on sozinho só garante a ordem de início, não que o banco já esteja aceitando conexões.

  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
Nada encontrado. Tente outra palavra, como "porta", "volume", "log" ou "permission".

Boas práticas

FaçaPor quê
Fixe a versão da imagem (nginx:1.27) em vez de latestEvita que uma atualização inesperada quebre algo no próximo pull.
Use restart: unless-stopped em serviços permanentesVolta sozinho após queda ou reboot do servidor.
Guarde dados em volumes e faça backupContainer é descartável, o dado não.
Segredos em .env fora do Git (e no .gitignore e .dockerignore)Senhas não devem ficar dentro da imagem nem no repositório.
Um processo principal por containerFica simples de monitorar, reiniciar e ver logs. Combine vários com Compose.
Use --rm em testes rápidosNão deixa lixo de containers parados.
Limite logs (max-size)Impede que um container verboso encha o disco do servidor.
Prefira imagens oficiais e -slim/-alpineMenores, mais rápidas para baixar e com menos superfície de ataque.
Não publique portas de banco na internetDeixe o banco só na rede interna do Compose; publique apenas o que precisa.

Fluxo do dia a dia com Compose

docker compose up -d --build   # sobe / atualiza
docker compose logs -f app     # acompanha
docker compose exec app sh     # entra para investigar
docker compose down            # desliga (dados preservados)

Com esses quatro comandos você resolve a maior parte do trabalho.
